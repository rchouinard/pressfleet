# UI

The Nuxt (Vue 3) + Tailwind dashboard for agency operators. It's built as a static SPA (`nuxt generate`, `ssr: false`) and embedded into the Go binary, so production needs no Node.js runtime (design doc §3). `pressfleet serve` serves it from the dashboard domain's root; the API lives under `/api/v1/` on the same origin, which is why the session cookie needs no CORS setup (design doc §4.5).

## Working on the UI

Node and pnpm are pinned in `mise.toml` (`mise trust && mise install`).

```sh
mise exec -- pnpm -C ui install     # once
mise exec -- pnpm -C ui dev         # http://localhost:3000, proxies /api and /healthz
mise exec -- make ui-check          # lint + typecheck + unit tests (what CI runs)
mise exec -- make ui                # nuxt generate -> ui/.output/public
mise exec -- make build             # binary with the UI embedded
```

`pnpm dev` proxies API calls to a `pressfleet serve` on `http://localhost:8080`; set `PRESSFLEET_DEV_API` for another address. The proxy keeps the browser on one origin, so cookies behave as in production.

| Script | Purpose |
| --- | --- |
| `dev` | Dev server with hot reload |
| `generate` | Static build into `.output/public` |
| `generate:api` | Regenerate `app/api/schema.gen.ts` (run by `make generate`) |
| `lint` | ESLint (Nuxt flat config) |
| `typecheck` | `nuxt typecheck` (vue-tsc, strict) |
| `test` | Vitest |
| `test:e2e` | Playwright, against a running platform (see below); `make test-ui-e2e` boots one |

Each dependency has a reason (CLAUDE.md). Versions are in `package.json` and `pnpm-lock.yaml`; CI installs with `--frozen-lockfile`.

## The generated API client

`app/api/schema.gen.ts` is generated by `openapi-typescript` from `api/openapi.yaml` and **never edited by hand**. `make generate` regenerates it along with the Go code, it is committed like the Go output, and CI's "generated code is up to date" step fails when it drifts from the spec. Change the spec, run `make generate`, commit both.

`app/utils/api-client.ts` (`createApiClient`) is the only code that calls `fetch` for the JSON API, and `useApi()` (in `app/composables/`) hands out the shared instance:

- Requests go to the page's origin with `credentials: 'same-origin'`; the `pressfleet_session` cookie is HttpOnly, so the UI never sees it.
- Unsafe methods (anything but GET/HEAD/OPTIONS) send `X-CSRF-Token` from `useCsrfToken()`. The login flow sets it from `csrf_token` in the login and `GET /api/v1/auth/me` responses.
- 2xx responses resolve as `{ data }`; every other response, and every network failure, **throws `ApiError`** (`app/utils/api-error.ts`).
- `onUnauthorized` is the hook for 401s; `useApi()` wires it to the login redirect (see "Session and roles").
- `onReauthenticationRequired` is the hook for a sensitive action refused until the session reauthenticates (`403` with the reauthentication problem type). The client clones each request before sending it, calls the hook, and when it resolves true sends the copy once more (body included, with the current CSRF token); when it resolves false the original `ApiError` is thrown. Concurrent refusals share one call. `useApi()` wires it to the reauthentication dialog (see "Two-factor sign-in and reauthentication").
- `onEnrollmentRequired` is the hook for a request refused because the session must enroll a second factor first (`403` with the enrollment problem type). The `ApiError` is still thrown; concurrent refusals share one call. `useApi()` wires it to go to the setup page (see "Two-factor settings and forced enrollment").

**Not for streams or binary bodies.** The wrapper reads JSON. Server-sent events (the site log stream) are read with `fetch` by `utils/log-stream.ts` (see "Logs viewer"), not `EventSource`: `EventSource` hides HTTP statuses and Problem Details and can't be told when to stop retrying. The session cookie is sent (same origin); a GET needs no CSRF header. Uploads and downloads (site imports, deploy packages, database and site exports) use a plain `fetch` or an `<a href>` against `apiUrl(...)`, with the CSRF header added by hand for unsafe methods. Keep those uses small and in one composable each.

## Conventions

These apply to #81, #82, #84 and later work.

### Layout

```
ui/
  app/
    api/schema.gen.ts   generated client types (do not edit)
    assets/css/         Tailwind entry (main.css)
    components/         UI components, PascalCase; domain components get a folder (components/site/SiteCard.vue)
    composables/        useXxx() functions that use Nuxt (state, router, data fetching)
    layouts/            page frames: default.vue (app shell), auth.vue (login)
    pages/              file-based routes; one file per screen
    utils/              pure TypeScript with no Nuxt runtime: API client, ApiError, role helpers
    app.vue, error.vue, app.config.ts
  tests/                Vitest specs, one per unit: tests/<name>.test.ts
  e2e/                  Playwright specs and fixtures (docs/testing.md); playwright.config.ts
  public/               static files copied as they are
  placeholder/, ui.go, embed_*.go   the Go package that embeds the build (see below)
```

Nuxt prefixes a component's name with its folder unless the name already starts with it: `components/alert/AlertTable.vue` is `<AlertTable>`, but `components/alert/ConfirmDelete.vue` would be `<AlertConfirmDelete>` and `<ConfirmDelete>` would silently render nothing. Generic components live directly in `components/`. `useCursorList()` is the shared "first page plus Load more" for list pages.

Code that should be unit tested goes in `utils/` or in components that don't need the Nuxt runtime, and imports what it uses explicitly (`import { ApiError } from '../utils/api-error'`) rather than relying on auto-imports. Vitest runs it without Nuxt that way. Anything that needs `useState`, `useRoute` and so on is a composable, covered by the typecheck and by the end-to-end checks.

### Data fetching

- Call the API only through `useApi()`; never `fetch`, `$fetch`, or `useFetch` against `/api`.
- Page data uses `useAsyncData(key, () => api.GET(...))`. Give each call a stable key. Mutations are plain `await api.POST(...)` in an event handler.
- Types come from the schema: `components['schemas']['Site']`, never hand-written copies. If a type is missing, the spec is incomplete: fix the spec.
- List endpoints use cursor pagination (`next_cursor`); don't load every page eagerly.

### Errors (RFC 9457 Problem Details)

- Every API failure arrives as an `ApiError` with `status`, `title`, `detail`, `requestId`, and `errors` (per-field validation messages for `422`; look one up with `err.fieldError('/php_version')` and show it next to the field).
- Use `toApiError(e)` in a `catch` to get an `ApiError` from anything thrown.
- Show failures with `<ProblemAlert :error="err" />` (or a toast built from `err.title` and `err.detail`). It includes the request ID, which operators quote when reporting an issue. Don't show raw `err.message` from non-API errors or stack traces.
- A failed page load renders the error in place, as the landing page does; reserve `error.vue` for unknown routes and bugs.
- `403` means the role can't do this. Hide controls the role can't use (below), but still handle `403`, because the API is the authority.

### Roles

The three roles are `admin`, `operator` and `viewer` (design doc §4.6). `roleAtLeast(role, 'operator')` in `utils/roles.ts` is the building block. See "Session and roles" below for the composable and the guard; use those rather than comparing role strings in components. UI hiding is a convenience, never enforcement.

### Accessibility, responsiveness, themes

- Use Nuxt UI components for anything interactive (they carry the ARIA and keyboard behaviour); label every icon-only button (`aria-label`).
- Mobile first: layouts work at 360 px wide, and tables scroll or collapse rather than overflow the page.
- Dark mode follows the system preference and the user's choice (Nuxt UI's color mode). Use semantic classes (`text-muted`, `bg-default`, `border-default`) instead of fixed colors so both themes work.
- Status is never conveyed by color alone: pair a badge's color with its text or icon.

### Content-Security-Policy

The server sends `script-src 'self'` plus the hashes of the few inline scripts Nuxt writes into `index.html`, and nothing else. So: no inline event handlers, no `eval`/`new Function`, no third-party scripts, fonts or images from other origins (`connect-src` falls back to `'self'`, too). Anything that needs a new origin means changing `contentSecurityPolicy` in `control-plane/internal/httpserver/static.go` deliberately. Check pages in a real browser after adding a library: a CSP violation shows in the console, not in the build.

### Testing

- Unit tests: Vitest, in `tests/`, no Docker and no network. The API client is tested with an injected fake `fetch` (see `tests/api-client.test.ts`); do the same for anything that calls the API.
- Component tests use `@vue/test-utils` `mount` for components that don't need Nuxt.
- `make ui-check` runs lint, typecheck and tests; CI runs the same, then `nuxt generate`.
- End-to-end tests: Playwright, in `e2e/`, against the embedded dashboard on a real platform (`make test-ui-e2e`). `make ui-check` lints and typechecks them (`tsc -p e2e`) but doesn't run them. How to run, write and debug them, and what they cover: [docs/testing.md](../docs/testing.md#dashboard-end-to-end-tests).

## App shell

### Session and roles

- `useSession()` returns `user`, `role`, `csrfToken`, `loading`, `isAuthenticated`, `refresh()`, `login()` and `logout()`. `middleware/auth.global.ts` loads the session once per page load (`GET /api/v1/auth/me`; this also restores the CSRF token), sends signed-out users to `/login?redirect=<path>`, and sends signed-in users on `/login` to their `redirect`. The target goes through `safeRedirect` (`utils/redirect.ts`): same-origin absolute paths only, never `//host`, backslashes, control characters or `/login`.
- A 401 anywhere mid-use (the API client's `onUnauthorized`, wired in `useApi()`) clears the session and goes to `/login?redirect=<current page>&expired=1`. The startup probe and the login request handle their own 401. If the control plane can't be reached at load, `error.vue` shows a retry instead of a login form.
- `pages/login.vue` is the sign-in form (email and password with a show/hide toggle, Problem Details in `ProblemAlert`, field errors, password cleared after a failure, disabled while submitting). `/account` (everyone: profile, own password, two-factor settings, own API tokens and SSH keys, sign out) and `/users` (Admin only, gated with `requires: 'user.view'`) are the #82 pages. A new token's secret exists only in the account page's memory while its dialog is open: never in storage, URLs or logs.
- Permissions: `utils/permissions.ts` is the one table of UI actions to minimum role, using the server's action names (`site.delete`, `user.view`, ...). `useCan().can('site.delete')`, `<IfCan action="site.delete">...</IfCan>` (with an optional `#denied` slot) and `can(role, action)` all read it. **Rule: hide what the role can't do; the server stays authoritative and 403s are still handled.** Add an action to the table (and to `authz.go`) before gating on it; `tests/permissions.test.ts` checks the table against design doc §4.6 and against the Go source.
- Gate a whole page with `definePageMeta({ requires: 'user.view' })`: lower roles get the 403 page.

| Minimum role | Actions |
| --- | --- |
| viewer | view sites, client groups, jobs, backups, monitoring (metrics and alerts); own password, tokens, SSH keys |
| operator | read site logs; create/import/update sites, domains, start/stop, maintenance, cache purge, retrieve credentials; deploy code, export database, read-only DB sessions; create backups, restore, approve core updates; create/update client groups; manage alert rules; create and delete staging sites |
| admin | delete sites (also with their backups); read-write DB sessions; delete/offboard client groups; manage users, reset their second factors, others' tokens, audit log; platform settings |

### Two-factor sign-in and reauthentication

Design doc §6.2 and docs/configuration.md "Dashboard two-factor authentication". Logic is in `utils/two-factor.ts` and `utils/webauthn.ts`; the components in `components/auth/` are Nuxt-free and tested with `mount` (`tests/login-second-factor.test.ts`, `tests/reauthenticate-dialog.test.ts`).

- **Second step**: a login that answers `401` with the second-factor problem type (`secondFactorChallenge`) shows `AuthLoginSecondFactor` in `login.vue`, offering only the problem's `methods`: a code field for an authenticator app (`autocomplete="one-time-code"`), "Use a security key or passkey", and "Use a recovery code" (`AuthFactorForm`). A wrong proof (`422`) stays on the step; `429` counts down `Retry-After`; `401` (the pending login expired or was used) goes back to the password with a message. Users without a second factor sign in in one step, as before.
- **Recovery codes**: after a recovery-code login, `AuthRecoveryCodesNotice` says how many codes are left (`recovery_codes_remaining`) and links to regenerate them (`RECOVERY_CODES_PAGE`, the account page's two-factor section) before going on.
- **WebAuthn**: `getAssertion` converts the API's JSON request options with `PublicKeyCredential.parseRequestOptionsFromJSON()` where the browser has it, else with the base64url helpers, calls `navigator.credentials.get()`, and sends the assertion in JSON form (`toJSON()` where available). Browser-side failures (no support, cancelled, timed out) are `WebAuthnError`s worded for the user.
- **Reauthentication**: `AuthReauthenticateDialog` is mounted once in `app.vue` and opened by `useReauthentication().ask()`, which the API client's `onReauthenticationRequired` calls. Each time it opens it loads `POST /auth/reauthenticate/options` (a fresh WebAuthn challenge) and offers the user's factors, or the password for users without one, then `POST /auth/reauthenticate` and the refused request is sent again. Cancelling surfaces the original `403`; a `401` closes it and the usual redirect to the login page follows.

### Two-factor settings and forced enrollment

`components/two-factor/TwoFactorSettings.vue` is the one copy of the settings, on the account page ("Two-factor authentication", `#two-factor`) and on the forced-enrollment page. It is Nuxt-free: the requests come in as a `TwoFactorClient` (`twoFactorClient(useApi())` in `utils/two-factor-settings.ts`), so `tests/two-factor-settings.test.ts` mounts it with a fake. It emits `changed` after each change and the page reloads the session (`two_factor_enabled`, `recovery_codes_remaining`, `enrollment_required`); after a first factor it waits until the recovery codes are closed.

- **Authenticator app**: "Set up" starts an enrollment (`POST .../totp`) and opens a dialog with the QR code (`TwoFactorQrCode`, `uqr` SVG as a `data:` image) and the secret, then confirms a code (`.../totp/confirm`). A wrong code stays in the dialog; an expired one (`404`) offers "Start again". "Remove" deletes it after a confirmation.
- **State**: the settings learn what the user has from one read, `GET /users/me/two-factor` (`client.status()`): the authenticator app, every key with the current relying party ID (`rp_id`), and the recovery codes left. It is loaded on mount and after each change, and starts no WebAuthn challenge; never infer factors from `two_factor_enabled` or call `POST /auth/reauthenticate/options` for them.
- **Security keys and passkeys**: `TwoFactorCredentialList`, labeled Synced (`backup_eligible`) or Device-bound with when each was last used. A key whose `rp_id` isn't the status read's `rp_id` (not the page's host, which a proxy can make differ; with none, no key is usable) was registered for an old domain: it says so and offers only Remove. Adding asks for a name, fetches the creation options when the dialog opens (so the browser prompt follows the click directly, and any reauthentication comes before it), calls `createCredential` (`utils/webauthn.ts`, `navigator.credentials.create()`), and registers the result; each failure gets a fresh challenge.
- **Recovery codes**: how many are left, and "Generate new codes" after a confirmation. New codes (also the first set, from the first factor) show once in a dialog that can't be dismissed by clicking outside, with Copy and a `data:` URL Download.
- **Removing** an authenticator app or key that is the last second factor while the role requires one answers `409` with the last-factor problem type; the dialog says to add another first.
- **Secrets**: the TOTP secret and URI exist only in the component's `totpSetup` while its dialog is open, and new recovery codes only in `codes` while theirs is; closing drops them. Never stored, in a URL or logged.
- **Reauthentication**: every change is sensitive. The API client's hook (above) asks and repeats the request, including a registration whose session went stale while the browser prompt was open; a cancelled check shows the `403`.
- **Forced enrollment**: when `GET /auth/me` says `enrollment_required`, the route guard sends every page to `/two-factor-setup` (auth layout, so the app shell's requests aren't made) with the page as `redirect` (`enrollmentRedirect` in `utils/two-factor.ts`). It shows the same settings and "Sign out"; once the first factor is set up and its recovery codes closed, the session is reloaded and the user goes on. Users who don't need it are sent from that page to `/account`. A session restricted mid-use (a promotion under `two_factor.required: admins`, a policy change) doesn't wait for the next navigation: the API client's `onEnrollmentRequired` (a `403` with the enrollment problem type; concurrent refusals share one call) runs `enrollmentRequiredHandler`, wired in `useApi()`, which reloads the session and replaces the route with the setup page, the current page as `redirect`. The refused request still throws its `403`.
- **Admin reset**: `/users` has a Two-factor column (On/Off from `two_factor_enabled`) and, with `user.two_factor.reset`, "Reset two-factor" for other users who have a factor (never for oneself, which the API refuses), confirmed with `ConfirmDialog` (`DELETE /users/{id}/two-factor`).

### Navigation registry

`utils/nav.ts` (`navRegistry`) is the only definition of the sidebar and drawer: `{ id, label, icon (i-lucide-*), route?, minRole, hidden?, section }`. Entries are filtered by role (`navFor`). An entry **with a `route` is a link** (active highlighting and `aria-current="page"` by path prefix); an entry without one shows dimmed with a "Soon" badge. **A page's PR adds `route:` to its entry; nothing else.** New areas append an entry. Pages set breadcrumbs with `useBreadcrumbs([{ label, to? }])` and their own `<h1>` and `useHead({ title })`. Icon names in `.ts` files are bundled because `nuxt.config.ts` makes the icon scanner read `.ts` files; use only bundled Lucide icons.

### Notifications and errors

- `useNotify()`: `error(e)` (ApiError with request ID, plain wording for 401/403/429/network), `success()`, `info()`, `jobStarted(job)` (toast with a "View progress" action). `utils/notify.ts` holds the formatting. Field errors still belong next to their fields.
- `plugins/errors.client.ts` turns unhandled rejections and render errors into a toast. `error.vue` renders 403, 404, 5xx and unreachable states inside the shell for signed-in users. `AppNetworkBanner` shows when the browser is offline or a request failed at the network level, and clears on the next answer.
- `plugins/chunk-reload.client.ts` reloads the page once when a script chunk fails to load before the first page has rendered (Nuxt's `app:chunkError`), which would otherwise leave it blank; a `sessionStorage` flag (`utils/chunk-reload.ts`) stops a chunk that keeps failing from looping, and is cleared once a page renders.

### Job progress

- `<JobProgress :job-id>` (live) wraps `<JobProgressView :job>` (pure, tested). `<JobLink :job-id>` links to `/jobs/<id>`. After a `202`, call `useNotify().jobStarted(data.job)`.
- `useJob(id)` follows `GET /api/v1/jobs/{id}/events` through `utils/job-stream.ts`: it merges `job` snapshots with `log` lines per step into whole `Job`s, ends after a terminal snapshot, reconnects on drops, stalls, 5xx, 408 and 429 (1 s doubling to 30 s) with `Last-Event-ID`, gives up on other 4xx, and disconnects while the tab is hidden (connections per server are few). If the stream can't be used (not an event stream, a 5xx `error` event, or two connections in a row without an event, as behind a buffering proxy) it falls back to polling `GET /api/v1/jobs/{id}` through `utils/job-poller.ts`: 1 s while running or rolling back, 2 s queued, x1.5 per quiet poll after three (cap 5 s); stops at `succeeded`/`failed`/`rollback_failed`, on unmount, and on 401/403/404; retries network errors, 5xx and 429 at 2 s doubling to 30 s while the last state stays visible; pauses while the tab is hidden and polls again on show or `online`; aborts the request in flight on stop.
- Steps show state, attempts, duration and a collapsible log (monospace, whitespace kept, text only, never `v-html`; follows new lines unless the user scrolled up). Failed jobs show the error and the roll-back outcome. Pages: `/jobs` (state and target filters, "Load more") and `/jobs/[id]`.

## Resource pages

`pages/client-groups/index.vue` is the reference for list/create/edit/delete pages (sites, users, alert rules and so on copy it). The pieces:

- **List**: `createPagedList(fetchPage)` (`utils/paged-list.ts`) holds `items`, `cursor`, `loading`, `loadingMore` and `error`. The page loads the first page inside `useAsyncData`, shows a first-page failure in place with `<ProblemAlert>`, and offers "Load more" while `cursor` is set (a failed later page is a toast, and the rows stay). Reload with `list.load()` after a mutation.
- **Table**: a domain component in a folder (`components/client-group/ClientGroupTable.vue`) that takes `canUpdate`/`canDelete` booleans and emits `edit`/`delete`; the page computes them with `useCan()`. That keeps the component Nuxt-free and testable, and the role matrix lives in `utils/permissions.ts` only. Hide the "New" button with `<IfCan>`; set `definePageMeta({ requires: '<x>.view' })`.
- **Form**: a modal (`ClientGroupFormModal.vue`) that takes the existing record to edit and a `submit(values)` callback. It validates client-side first (rules in `utils/<x>.ts` mirror the spec), then shows 422 `fieldError('/name')` next to the field and any other failure in `<ProblemAlert>`, keeps the modal open while saving, and closes it on success. PATCH sends only changed fields (`updatePayload`).
- **Delete**: `<ConfirmDialog v-model:open :busy :error @confirm>` is generic. The page runs the request; on failure it passes the `ApiError` back (a `409` for a group with sites shows the server's wording and request ID in the dialog), on success it closes the dialog, toasts and reloads.
- **Nav**: the page's PR sets `route:` on its registry entry and nothing else.

Tests: pure logic in `utils/<x>.ts` (payloads, validation, gating via `can()`), the table with `mount` and a stubbed `UButton`, and `paged-list` with a fake `fetchPage`.

## Sites

`/sites` (list) and `/sites/<id>` (detail); `/sites/<id>/logs` is the logs viewer below. Rules for the pieces in `components/site/` and `utils/site.ts`:

- **List**: `createPagedList` with a client group, a status and an environment filter (production or staging; the API's `environment`); each reloads the first page. The table is read-only for every role; its name links to the detail page. "New site" shows with `<IfCan action="site.create">`.
- **Provisioning**: `SiteFormModal` (client-side checks in `validateSite`, 422 field errors next to the fields). On `202` the page toasts, then goes to the new site's page, where the job is followed live. A blank admin username is omitted so the server generates one. PHP version is a select over the catalog (`usePhpCatalog`, `phpCreateOptions` in `utils/php.ts`): "Platform default" (with the catalog's `default` and its status) is preselected and sends no `php_version`, then the versions not past end of life, each with its status; a chosen version near end of life gets the warning. If the catalog fails to load, only the platform default is offered and the failure is shown with `ProblemAlert` (it is retried when the form opens again).
- **Detail**: status, domains, settings, and "Recent jobs" (`GET /jobs?target_type=site&target_id=`). The newest unfinished job is shown with `<JobProgress>` and stays on screen after it ends until dismissed; when it ends the page reloads the site and jobs, and a successful `site.delete` returns to the list. Start (stopped sites) and Stop (running sites) need `site.start`/`site.stop`; neither is offered for sites that are busy or failed, where the API answers `409`. Delete (`site.delete`, admin) goes through `<ConfirmDialog>`; the site then shows as "Deleting" with its job. The dialog holds `SiteDeleteBackups` (`site.delete_with_backups`, admin): "Also delete this site's backups", unchecked each time the dialog opens, with the number of snapshots that would go (`countSnapshots` in `utils/site-delete.ts` reads `GET /sites/{id}/backups`, at most 10 pages of 200, counting restorable backups) and a "can't be undone" warning once checked; the choice is sent as `?delete_backups=true` (`deleteSiteQuery`).
- **Admin password, once**: the API generates it at creation and returns it only from `POST /sites/{id}/admin-credentials` (`410` afterwards). The detail page offers "Reveal admin credentials" (`site.credentials.retrieve`, operator) only while `admin_credentials_available` and the site is settled (`showCredentialsAction`). The response is held in one component ref while a non-dismissible dialog is open (`SiteCredentials`: copy buttons, selectable fields, a clear "only once" note) and dropped when the user confirms; it is never stored, put in the URL, or logged.
- **Log in to WordPress** (`SiteAdminLogin`, `utils/admin-login.ts`; `site.admin_login`, operator, so viewers don't see it): the header button opens wp-admin as the site's default administrator (§5.9). The click handler opens a named blank tab *synchronously* (popup blockers refuse `window.open` after an `await`), then calls `POST /sites/{id}/admin-login` and submits a hidden form with the `token` field (method POST, `target` the tab) to the returned `url`; on any failure the tab is closed and the problem shown. The token is a local variable for that moment: never in a URL, state, storage or a log. The `409` with `CHOOSE_USER_PROBLEM_TYPE` (imported site, deleted default) closes the tab and shows a picker from `GET /sites/{id}/administrators`; picking one opens a fresh tab in that click. "Log in as..." in the dropdown opens the same picker even when a default exists. The button is disabled with the reason unless the site is `running` and out of maintenance, and a note says the browser will ask for the preview credentials when preview protection is on and the site isn't live.

## Staging sites

Design doc §5.11, plan `docs/staging-clones-plan.md`. A staging site is a `Site` with `environment: 'staging'`, its production site in `parent_site_id` and a `staging` object. Logic is in `utils/staging.ts` (`tests/staging.test.ts`, `tests/staging-components.test.ts`).

- **Production page**: `SiteStagingCard` lists the staging sites (`GET /sites?parent_site_id=`, owned by the page, which reloads it every 5 s while one is provisioning or deleting) and opens `SiteStagingFormModal` (name, "a fresh copy" or "an existing backup" from the site's restorable backups, optional resources; blank means as production). The `202` carries the one-time preview login, held in the card's `created` ref while a non-dismissible `SitePreviewCredentials` dialog is open; closing it goes to the staging site's page, where the `site.clone` job is followed as after "New site". The card is not on staging sites, which can't be nested (`stagingBlockedReason` also explains a busy production site). A failed clone stays in the card with its `status_message` and a Delete button.
- **Staging page**: `SiteStagingBanner` names the production site (link), when the copy was made and last pushed, and has an `actions` slot where #208 puts refresh and push. Domains and go-live are not shown. The settings get an "Outbound email" switch (`PATCH outbound_mail`, a job, like preview protection).
- **Deleting**: Operators delete staging sites (`site.staging.delete`); production sites stay Admin (`site.delete`), and the backups option stays Admin. A production site with staging sites lists them in the dialog (confirm disabled); a `409` from the server shows its wording naming them.
- **Lists**: `SiteEnvironmentBadge` marks staging sites. `SiteTable` shows each staging site under its production site (`arrangeSites`); one whose production site isn't in the loaded rows (another page, filtered out) stays in place with "Staging site of <name>", looked up with `GET /sites/{id}`. Pickers use `siteOptionLabel`.
- **Refresh and push** (#208): `SiteStagingSync` is in the banner's `actions` slot and owns the buttons (`site.staging.refresh`, `site.staging.push`, Operator; hidden by `IfCan`) and the two dialogs, `SiteRefreshDialog` and `SitePushDialog` (props only). Logic and wording are in `utils/staging-sync.ts` (`tests/staging-sync.test.ts`). A button that can't work now stays disabled with the reason under it (`refreshBlockedReason`, `pushBlockedReason`; the push needs a running production site, read fresh each time a dialog opens).
  - **Refresh**: files (all, code only, none) and database, at least one, from a fresh production backup or an existing one. The dialog lists what the choice replaces, including that all files and code only remove files production lacks. The staging page stays and follows the `site.refresh` job.
  - **Push**: starts at code only without the database. It lists only the warnings that apply to the scope (`pushWarnings`): a database push replaces what production recorded since `database_as_of`, and all files replaces production's `uploads` (media added since is lost) since `uploads_as_of`. The two times are separate and are the snapshot time each part was last copied from, not the last refresh or push. A null time says its age isn't known and the loss may go back to when the site was copied from production. Always: maintenance mode during the push, the pre-push backup and rollback, settings not pushed, and PHP or core differences. A push with the database or all files asks for production's slug (a dashboard gate; the API doesn't enforce it).
  - **Core guard**: a `422` on `/database` is shown in the server's words with a link to production's "WordPress core" card (`#site-core-heading`).
  - **After a push** the operator lands on the production site's page, where the job is (its target is the production site) and the "Job progress" section follows it. `JobProgressView` shows the job's undo point (`pre_push_backup_id`, or `pre_restore_backup_id` for a refresh) with a link to `/sites/<id>/backups?backup=<id>`, which marks that backup "Undo point". A failed push rolls back and leaves production in maintenance mode with a status message; the site page shows it as "This site is in maintenance mode" with the reason.
- **Jobs**: `site.clone` is "Create staging site". A job with `after_job_id` shows "Waiting for job" (queued) or "Ran after job" with a link, in `JobProgressView` and `JobTable` (`waitsFor`).

## Go-live and domains

The site page's "Domains" section is one mount, `<SiteDomains :site @changed>`. It wraps `SiteDomainsPanel` (props and callbacks only, tested with `mount`), which calls `POST /sites/{id}/go-live` and `PUT /sites/{id}/aliases` through `SiteDomains`. Logic is in `utils/domains.ts`.

- **Role and state**: controls need `site.domains.manage` (operator); others only see the domains. Go-live (and "Change primary domain") needs a `running` site; editing aliases needs a live site that is `running` or `stopped`. In other states the section says why instead of offering a button (the API would answer `409`).
- **Validation**: domains are trimmed and lower-cased, aliases are typed one per line (max 20, no repeats, none equal to the primary). The server's `422` stays authoritative.
- **DNS check**: a `422` of the DNS problem type (`DNS_CHECK_PROBLEM_TYPE`) is shown as a per-domain list (`errors[].field` is mapped back to the domain that was sent), says nothing changed, and turns the button into "Check again". "Skip the DNS check" (`skip_dns_check`) is for hosts behind a CDN or load balancer. A check that couldn't run has no entries; its `detail` is shown.
- **Job**: on `202` the panel toasts, closes the form and emits `changed`; the page reloads the site and jobs, and the usual "Job progress" section follows the new job (`<JobProgress>`).

## Site settings and core updates

On the site page, after "Domains": `<SiteSettings :site @changed>` wraps `SiteSettingsPanel` (props and callbacks only, tested with `mount`) and `<SiteCoreCard :site @changed>` shows WordPress core. Logic is in `utils/site-settings.ts` and `utils/php.ts`, which only maps the API's status to a badge and warning (`tests/site-settings.test.ts`).

- **Roles and state**: PHP, limits and preview protection need `site.update`, maintenance `site.maintenance.set`, cache purge `site.cache.purge` (all operator); viewers see the values. While the site is provisioning, updating, deleting or failed the controls are replaced by the reason (the API answers `409`).
- **PHP and EOL**: the versions, statuses and dates come from `GET /api/v1/catalog/php-versions` (`usePhpVersions`; nothing is copied into the UI). A current version past end of life, or within 180 days of it, gets a warning with an icon and text. The selector never offers EOL versions (the server answers `422`); its `422` shows next to the field.
- **Limits**: validated like the spec (CPU number, reservation >= 32, limit >= 64 and >= reservation); only changed fields are sent (`PATCH /sites/{id}`).
- **Jobs**: update, maintenance and purge answer `202`; the page toasts and its "Job progress" section follows the job.
- **Preview password, once**: turning protection on for the first time (`preview_credentials` of the PATCH response) and "Generate a new password" (confirmed first; `POST /preview-password`) return the password. It is held in one ref while a non-dismissible dialog (`SitePreviewCredentials`) is open and dropped when the user confirms; never stored, in a URL or logged.
- **Core**: shows version and branch, whose policy applies, the next release, a major release waiting for approval, branch warnings and a failed update. Operators (`core_update.approve`) can hold the branch, approve the pending major branch, follow the client group again (`PUT /core/policy`), or "Update now" (confirmed; `POST /core/update`, a job; only for running sites with a target).

## Logs viewer

Operators and Admins only (`logs.view`; Viewers can read metrics and alerts but not logs, #181): the sidebar entry and the site page's "Logs" button are hidden from Viewers, and both log pages are gated with `requires: 'logs.view'`. The API enforces it.

`/logs` picks a site (the sites list API), `/sites/<id>/logs` shows it: a "Runtime" tab (`SiteLogViewer`, takes a site id) and a "Jobs" tab (`SiteJobLogs`, `GET /sites/{id}/job-logs`, newest first, "Load older").

- **Data flow** (`composables/useSiteLogs.ts`): "Live tail" follows `GET .../logs/stream`; any other time range reads `GET .../logs` newest page first. Both fill one bounded buffer (`utils/log-buffer.ts`, 5,000 lines; the oldest are dropped while following, and history never evicts the newest lines). "Load older lines" pages backwards: `until` the first line shown, then the API's `next_cursor`.
- **Stream** (`utils/sse.ts` parser, `utils/log-stream.ts` connection, both free of Vue): reconnects with 1 s doubling to 30 s plus jitter and sends `Last-Event-ID`, so the stream continues after the last line instead of repeating the tail; gives up on 4xx other than 408/429 and on an `error` event (a "Reconnect" button restarts from the tail); treats 45 s without any bytes (the server sends a keep-alive every 15 s) as dead. Pause closes the connection and resume continues from the last line, so nothing is lost or held in memory.
- **Safety**: lines render as text only (`SiteLogLine`; never `v-html`); a line over 2,000 characters is cut behind a "show more" button, and the SSE parser drops lines over 1 MiB. Search, source and level filters are applied by the server.
- **Accessibility**: the log box is `role="log"` with `aria-live="off"`; the only live region is the coarse status (Live, Paused, Reconnecting, ...). Auto-scroll stops when the user scrolls up and "Jump to latest" brings it back.

## Backups and restore

`/sites/<id>/backups` (linked from the site page's "Backups" button; `backup.view` to see it). Pieces in `components/backup/`, logic in `utils/backup.ts`:

- **History**: `BackupTable` over `createPagedList` (`GET /sites/{id}/backups`, "Load more"). Status always has an icon and text; a succeeded backup whose snapshot was removed by retention shows "Expired" and can't be restored; failure messages show under the status.
- **Back up now** (`backup.create`): `POST /sites/{id}/backups`; offered unless the site is provisioning, deleting or failed (`canBackUpSite`, the API's `409`s).
- **Schedule**: `BackupScheduleCard` shows the schedule and next run; with `backup.create` it edits it in place (`PUT /backup-schedule`: interval from the spec's allowed values, start hour in UTC or "platform window" which is the API's `null`). 422s show next to the fields.
- **Restore** (`backup.restore`, running sites only): `BackupRestoreDialog` states that the site's database and `wp-content` are overwritten, that a pre-restore backup is taken and the site goes into maintenance mode, and requires typing the site's name before the button enables. The page runs the request; failures (`409`, `422`) show in the dialog.
- **Jobs**: backup and restore return a job, followed with `<JobProgress>` on the page (an unfinished job of the site is picked up on load). When it ends the site, history and schedule reload. Restore and "Back up now" are disabled meanwhile.
- Restoring another site's snapshot (`source_site_id`) is not offered; the API supports it but the MVP UI restores the site's own backups.

## Developer workflows

Site import, code deployment, SSH keys and database access (design doc §5.7, §5.8). Pages are linked from the sites list and the site page, and gated by the permission table.

| Page | Needs | What it does |
| --- | --- | --- |
| `/sites/import` ("Import site" on `/sites`) | `site.import` | Client group, a `wp-content` archive and a SQL dump, uploaded with progress; then `POST /sites/import` and the job is followed in place. The result links to the new site. A completed upload is reused if only the import request failed. |
| `/sites/<id>/deploy` | `site.code.deploy` | Theme, plugin or must-use plugin, directory name, package (zip or tar.gz), "activate"; uploads, then `POST /sites/{id}/deploy` and follows the job (it rolls back by itself on a failed health check). Running sites only. |
| `/sites/<id>/database` | `site.database.export` | Export: starts the job, then offers a plain `<a href download>` to the download path (built from the job result's IDs, never from a URL in it). The newest unexpired export is offered again after a reload. Sessions: open (read-only; read-write only with `site.database.session.create_read_write`), list, end. |
| Site page, "SFTP" card | any role sees it | `sftp -P <port> <slug>@<dashboard host>` with copy buttons. The API doesn't report `sftp.port`, so the card shows the default (2222) and says to use the configured one if changed. |
| `/account`, "SSH keys" (`components/ssh/`) | any role | Add (paste a public key) and remove your keys; says that only Operators and Admins can connect. |

- **Uploads** (`composables/useUpload.ts`, `utils/upload.ts`): the resumable protocol of `/api/v1/uploads`. The file is hashed first with the incremental `utils/sha256.ts` (Web Crypto can't hash a multi-gigabyte file in slices) and the checksum declared on create; chunks (at most 16 MiB and the server's `max_chunk_bytes`) are PATCHed with `XMLHttpRequest`, the only way to get upload progress, with the CSRF header set by hand. A failed chunk is retried after asking `received_bytes`; a cancelled or failed upload is deleted. The other calls go through the generated client. `<UploadProgressBar>` shows the phase and bytes.
- **Downloads** need no composable: a same-origin `<a href download>` sends the session cookie (GET, so no CSRF header) and the browser streams the file to disk.
- **Secrets shown once**: a database session's password and tunnel command exist only in the page's `opened` ref while the dialog is open (not dismissible by clicking outside); closing drops them. They are never stored, in a URL or logged.
- Job types for import, deploy and export are labelled in `utils/job.ts`.

## Metrics charts

`/metrics` (platform, §7.2) and `/sites/<id>/metrics` (site, §7.1, linked from the site page) are one component, `<MetricsDashboard scope="platform|site">`, over `GET /api/v1/metrics/catalog` and the two range-query endpoints. Logic lives in `utils/metrics.ts` (tested in `tests/metrics.test.ts`).

- **Library: uPlot** (~50 KB minified, no dependencies, canvas). ECharts and Chart.js are several times larger for features we don't use (pie, maps, animation); a hand-written SVG chart would have to redo axes, cursor and resize. uPlot only runs in the browser, which suits `ssr: false`, uses no `eval` or inline scripts (the CSP allows it), and handles hundreds of points per chart without effort. It's imported lazily inside `MetricsChart` and its CSS ships with that component. The catalog groups metrics, so a page makes one request per group: a failing group shows its own error and Retry and the rest still draw.
- **Range and step**: presets (1 h to 30 d) end at now; "Custom" takes local from/until (blank until means now, and the future isn't requested). `chooseStep` aims for about 300 points, rounds up to a round step (15 s, 1 min, 5 min, 1 h, ...), never goes below the catalog's `min_step_seconds`, and raises the step if the catalog's `max_points` would be exceeded. Ranges beyond `max_range_seconds` are rejected in the form.
- **States**: loading skeletons per group, `ProblemAlert` per failed group (a `503` when the metrics store is down), and "No data" per metric. Collectors (#68 to #74) may not exist, so empty is normal: when nothing in the range has data, the page says so once instead of showing a wall of empty charts, and metrics without data are listed in one muted line per group. Timestamp-unit metrics (TLS expiry, last backup) are shown as dates, not lines.
- **Accessibility and themes**: the canvas is `role="img"` with a generated text summary; each card has a table of latest/min/avg/max per series, which also serves as the legend. Series differ by dash pattern as well as colour. Colours are re-picked and the chart rebuilt on a colour-mode change. Cards stack on one column at 360 px and the tables scroll horizontally.

## Platform overview

`/overview` (any role, `monitoring.view`) shows host capacity, reservations against host memory, and platform health. Logic is in `utils/overview.ts` (tests in `tests/overview.test.ts`); each panel loads and fails independently.

- **Capacity figures**: `GET /api/v1/metrics/platform/summary` with an explicit metric list (CPU, memory, fullest disk, MariaDB connections, Redis memory, job queue, job failure rate). Missing data shows as a dash, not an error.
- **Reservations vs host memory** (design doc §4.1): one request, `GET /api/v1/platform/capacity`. The server sums `memory_reservation_mb` of sites that are not `stopped` or `deleting`, compares it with the host's memory, and reports the level (90% or more is `caution`, over 100% `exceeded`, no host memory data `unknown`, never `ok`). The thresholds live only on the server; `assessCapacity` just words the level.
- **Platform health**: `/readyz` checks, read with plain `fetch` because the API client throws on the `503` that carries the failing checks.
- **Doctor results**: the API has no endpoint for `pressfleet doctor` results, so the page says to run it on the host. Replace that panel when an endpoint exists.

## Embedding in the Go binary

`go:embed` can't reach outside a package directory, and the Nuxt output lives in `ui/.output/public`, so `ui/` is also the Go package `github.com/rchouinard/pressfleet/ui`, which exposes the files as an `fs.FS`:

- **Default build** (no tag): embeds `ui/placeholder/`, a committed one-page notice. `go build`, `make test` and the linters therefore work on a machine without Node.js, and the repository holds no build output.
- **`-tags webui`**: embeds `ui/.output/public` (gitignored). If the directory is missing the build fails, so a release can't silently contain the placeholder.

`make build` picks for you (`UI=auto`): if `pnpm` is on the PATH it runs `make ui` when the sources changed and builds with the tag; otherwise it embeds the placeholder, and `pressfleet serve` logs a warning saying so. `make build UI=yes` requires Node (it fails without it), `UI=no` forces the placeholder, and `UI=prebuilt` embeds an existing `ui/.output/public` without building it (CI downloads the output of its UI job). The container image (`control-plane/Dockerfile`) builds the UI in a Node stage and compiles with the tag.

`httpserver.WithUI` serves the embedded files for everything the API doesn't own:

- `/api/*`, `/healthz`, `/readyz` and every method other than GET and HEAD go to the API, so an unknown API path gets a Problem Details `404`, never `index.html`.
- A path that matches a file is served with its content type, an `ETag`, and gzip for compressible files. Files under `/_nuxt/` carry a content hash in their names and get `Cache-Control: immutable` (except `/_nuxt/builds/latest.json`, which the app polls for new releases). Everything else, `index.html` included, gets `no-cache` so a new release applies at once.
- A path with no file that has an extension, or is under `/_nuxt/`, is a `404`. Any other unknown path is an app route and gets `index.html`, which the client-side router handles.
- Every response carries the Content-Security-Policy (see above), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (and `frame-ancestors 'none'`), and `Referrer-Policy: same-origin`.

Traefik routes the dashboard domain to the control plane by host only (`Host(<dashboard_domain>)`, all paths), so the UI is served at that domain's root.
